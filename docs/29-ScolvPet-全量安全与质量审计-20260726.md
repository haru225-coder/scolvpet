## 1. P0-1｜登出永久失效：0039 token 撤销被幂等重放绕过

> **状态：已修复并验证（2026-07-26）**。`deleteSession` 去掉 `RunIdempotent` 包装；`RunIdempotent` 的重放查询开始判定 `expires_at`，过期记录改为重新领取而非永久重放。两条回归测试均确认"修复前失败、修复后通过"，详见本文 §9。

**位置**：`api/internal/httpapi/server.go:333-336`、`api/internal/store/postgres.go:179-199`

```go
payload := []byte(`{"action":"logout"}`)      // 固定载荷
key := r.Header.Get("Idempotency-Key")
if strings.TrimSpace(key) == "" {
    key = "logout-" + ownerID.String()         // 固定键
}
```

三个条件叠加构成缺陷：

1. 无幂等键时，键与载荷都是**账号维度的常量**，method/path/payload 哈希每次完全一致；
2. `RunIdempotent` 的重放 SELECT **不过滤 `expires_at`**，记录写入时标 `now()+24h` 但该字段从未被读取；
3. 全仓无 `idempotency_record` 清理逻辑（仅测试 teardown 里有 DELETE）。

**已验证的存储形态**：204 响应被存为 `response_status=204`、`response_body={"body":"null","headers":{}}`，两者均非 NULL，因此第二次请求必然命中重放分支。

**后果**：用户第一次登出后，此后任何不带 `Idempotency-Key` 的登出请求都直接返回 204，而 `RevokeAccess` / `RevokeRefresh` / `RevokeAllRefreshForOwner` **一次都不执行**。手机丢失后在新设备点"退出所有设备"，服务端回 204 成功，旧设备的 access token 与 refresh token 继续有效 30 天。0039 迁移新建的 `revoked_token` 表在这条路径上永远不会被写入。

**修复**：登出是状态收敛操作，本身天然幂等，应直接移除 `RunIdempotent` 包装；或将默认键改为 `"logout-" + digestHex(accessToken)`。无论如何，`RunIdempotent` 的 SELECT 必须补 `AND expires_at > now()`，并为该表建立过期清理任务。

## 2. P0-2｜租户劫持：未经同意的邀请在登录时被静默接受，且顶替本人 owner 身份

> **状态：已修复并验证（2026-07-26）**，但**附带一处能力缺口**，需要产品决策收尾。详见 §10。

**位置**：`api/internal/store/principal.go:63-80`（自动接受）、`principal.go:127-131`（排序）、`api/internal/httpapi/p1_members.go:100-120`（邀请无同意校验）

攻击链三步：

1. `inviteOrganizationMember` 只校验手机号格式（`memberPhonePattern`，纯 6-20 位数字）与角色，**不校验该手机号是否同意、是否已有账号**。任意注册用户 A 可对受害者 B 的手机号发出 staff 邀请。
2. B 下次登录，`ResolveLoginPrincipalTx` 把最新一条 `status='invited'` 的邀请**静默 UPDATE 为 active**，无任何确认交互。
3. `resolvePrincipal` 的排序是 `CASE WHEN role='owner' THEN 1 ELSE 0 END` **升序** —— 非 owner 排 0、owner 排 1，攻击者授予的 staff 身份**排在 B 自己的 owner 身份之前**。

### 实证复现

在临时 PostgreSQL 15.17 上跑完全部 39 个迁移，构造"受害者已拥有自己的宠舍"场景后执行 `principal.go` 的原始 SQL：

```
① V 登录，自动接受语句 → 已静默接受邀请 role=staff owner=aaaaaaaa-...0001（攻击者）
② resolvePrincipal 解析 → OwnerID=aaaaaaaa-...0001  Role=staff
   （攻击者A=aaaaaaaa-...0001，V自己=bbbbbbbb-...0002）
```

**后果**：B 的 `principal.OwnerID` 变成 A 的 owner_id。B 的 App 此后所有请求都作用在 A 的租户上——B 看不到自己的仓鼠、客户、合同，而 B 新录入的全部数据写进 A 的宠舍。只需知道对方手机号。反向利用（诱导受害者把数据录入攻击者租户）同样成立。

### 关于"这是不是有意设计"

`store/principal_integration_test.go:14` 的 `TestResolveLoginPrincipalAcceptsNewestInviteAndRevocationFallsBack` 明确断言自动接受 + 非 owner 优先是预期行为。但该测试用的是**尚无自有宠舍的新账号**——即员工入职场景。测试从未覆盖"被邀请者本身已是 owner"的情形，而这正是漏洞窗口。因此这属于设计缺口而非纯实现 bug，修复需要产品决策配合。

**修复**：邀请必须显式接受（新增 `POST /v1/organization-members/invitations/{id}/accept`），登录时只列出待接受邀请、不自动 UPDATE；同时 `resolvePrincipal` 默认应优先选本人 owner 身份，组织切换由客户端显式指定并落到会话。

## 3. P1 清单

### 3.1 API｜`auth.Service` 互斥锁跨越数据库调用 → 全局串行化 + 连接池死锁
> **⚠️ 复核后升级为 P0（2026-07-26）：已实测复现，见 §11。4 个并发 refresh 即永久锁死进程，需重启。**
> **✅ 死锁部分已修复并验证，见 §15。全局串行化（`ParseAccessTokenContext` 持锁做 DB 往返）尚未处理。**
`api/internal/auth/service.go:249-286`。每个带 Bearer 的请求都在同一把进程级互斥锁内做两次 DB 往返（`IsAccessTokenRevoked` 内还先跑一条 `DELETE FROM revoked_token`），鉴权吞吐被压成单线程 DB 延迟的倒数。更严重的是死锁：`refreshSession`/`deleteSession` 在 `RunIdempotent` 外层事务已持有一个池连接的情况下，回调里调用 `s.Auth.Refresh`/`RevokeAccess`，后者先抢 `s.mu` 再申请第二个连接。`DB_MAX_CONNS` 默认仅 8，**8 个并发 refresh 即可锁死整个 API**，且 `http.Server.WriteTimeout` 不取消 request context，请求将挂起至进程重启。

### 3.2 API｜`clientIP` 无条件信任 X-Forwarded-For → IP 限流完全可绕过
`api/internal/httpapi/server.go:673-688`。取 XFF 首段（客户端自填），无可信代理白名单。所有 `sms:ip:`、`cust-sms:ip:`、`public:*:ip:` 桶均可通过轮换伪造值绕过，仅剩每号码 5 次/小时的 phone 桶，因此可对海量号码无限发短信。附带两个副作用：`auth_rate_limit` 表无清理逻辑，每个伪造 IP 留一行永久数据；`bucket_key varchar(200)`，XFF 超 193 字符触发 Postgres 22001 → 500。

### 3.3 API｜access/refresh token 明文永久存储在 `idempotency_record`
`api/internal/httpapi/server.go:258-267` + `store/postgres.go:222-234`。`issueSessionResponse` 的响应体含 token 原文，被整体 `json.Marshal` 写入 `response_body`，每次 refresh 轮换同理。结合 P0-1 的"永不过期、永不清理"，任何一次数据库读权限泄露（备份、只读副本、运维误操作）都等同于拿到全量历史会话凭据。这与 0039 迁移自己的注释直接矛盾：*"Store only the SHA-256 digest of the bearer token; the raw credential never enters the database."*

### 3.4 API｜公开能力令牌被写入访问日志
`api/internal/httpapi/server.go:594-608` 记录完整 `r.URL.Path`，而 `/v1/public/documents/{token}`、`/v1/public/shares/{token}` 的路径本身即凭据，且 `public_token` **无有效期**（仅 revoke 时置空）。一旦进入日志聚合系统即长期可用。

### 3.5 数据库｜复合外键 `ON DELETE SET NULL` 会把 NOT NULL 的 owner_id 一并置空（系统性，7 处）
`db/migrations/0036_doc_reservation_fk.sql:10-14`，同模式还见于 0019、0020(×2)、0021、0023、0028、0032。PostgreSQL 对未指定列清单的 SET NULL 会把**全部引用列**置 NULL，包含 `doc_document.owner_id`（NOT NULL）。

**实证**（PostgreSQL 15.17）：
```
ERROR:  null value in column "owner_id" violates not-null constraint
CONTEXT: UPDATE ONLY "child" SET "owner_id" = NULL, "ref_id" = NULL WHERE ...
```
当前只做软取消所以是潜伏缺陷，但任何硬删除/GDPR 清理路径都会以 23502 失败。修复需一个新迁移逐个重建这些约束为 `ON DELETE SET NULL (reservation_id)`。

### 3.6 移动端｜退出登录不清理业务控制器内存状态 → 跨账号数据残留
`apps/mobile/lib/ui/shell/mine_page.dart:296`、`lib/core/app_state.dart:245-264`。`logout()` 只清 token、prefs 与身份字段；`I2Controller.snapshotState`（仓鼠/笼盒全量）、CRM 联系人、合同列表、`AssistantController.turns`（聊天记录）驻留在 app 生命周期单例 `AppServices` 中原样保留。A 登出、B 在同一进程登录后会先看到 A 的数据，助手聊天记录甚至没有刷新机制。

### 3.7 Web｜媒体代理放行 `image/svg+xml` → 同源存储型 XSS
`apps/web/src/server.mjs:620`（`contentType.startsWith('image/')`）、`:860-868`（原样回传上游 Content-Type，无 nosniff、无 Content-Disposition、无 CSP）。上游媒体只要是 SVG，浏览器直接访问 `/p/{slug}/media/{id}` 就会当文档渲染并执行内嵌脚本。该路径与 `/p/{slug}`、`/d/{token}` 同源，脚本可读同源页面、发起同源 POST、窃取 URL 中的 `result` flash id。修复成本极低：MIME 白名单 + `X-Content-Type-Options: nosniff`。

### 3.8 小程序｜生产环境守卫 fail-open，永不触发
`apps/miniprogram/utils/config.js:3-9`。`APP_ENV` 与 `API_BASE` 均为源码硬编码常量，全仓无任何 CI 注入/构建替换机制；守卫要求 `APP_ENV === 'production'` 才检查，而该值恒为 `'development'`，**守卫恒为假**。按现状打包上传，正式小程序会把真实客户手机号、验证码、`ct_*` token 全部发往 staging 主机 `p.scolv.com:8443`——而该主机默认 `SMS_PROVIDER=mock`、`SMS_MOCK_CODE=123456`。这与 Android 侧 `make release-android` 的 fail-closed 标准严重不对等。

> 另有一项 `wx.login`/OpenID 完全未接线（全目录 grep 命中数 0，`project.config.json` 仍是 `touristappid`），`CORE_CODE_FREEZE.md:71` 已列为待办，此处仅记录其安全影响：客户身份 100% 依赖短信，放大了下述验证码轰炸面。

## 4. P2 精选（完整 30 项见各分节）

**权限与隔离**
- RBAC 对**所有 GET 全角色放行**（`rbac.go:83-86`）：viewer 及任何未知角色可读全部财务流水、客户 PII、含 `public_token` 的合同回执、全体成员手机号。
- RBAC 用 `strings.Contains` 判定路径归属（`rbac.go:96-136`）：breeder 只要路径任意位置含 `/hamsters`、`/media`、`/genetic` 即放行写操作，对新增路由极脆弱；肯定名单用 `Contains`、否定名单用 `HasPrefix`，两套语义混用。
- 助手 confirm 成为越权通道（`rbac.go:120-123` + `p2_assistant.go:262-369`）：staff 直接调 `/v1/enclosures`、`/v1/weight-records` 会被拒，但通过 `/v1/assistant/actions/{id}/confirm` 可执行同样的写操作。
- 无 refresh token 复用检测（`auth_persistence.go:101-116`）：`LookupRefreshSession` 漏检 `consumed_at`；检测到复用时不吊销整个 token 家族，被盗 token 抢先轮换后攻击者可无限续期。

**幂等与并发**
- 公开幂等键为全局命名空间（`customer_api.go:44-46` 用 `"cust-code-"+phone`）：知道手机号即可在 5 分钟 TTL 内重放拿到受害者的 `verification_id`，或抢占该键使受害者收不到新短信。接管 stale claim 时还会覆盖 `request_hash`，30 秒后可夺取他人 in-flight 键。
- claim-row 30 秒接管窗口导致副作用重复执行（`auth_persistence.go:226-296`）：接管只更新 `locked_at`、不标记新 owner，原 owner 慢于 30s 时两边都会真实发一次短信，代码里的 "Lost claim" 检测实际检测不到。
- `appendEvent` 用 `max(version)+1` 取号（`store/postgres.go:472-485`）：Read Committed 下并发写同一聚合必撞唯一约束，两处都不重试。
- 匿名请求可向租户的 `idempotency_record` 无限写入（`p3_growth.go:653-700`）。

**性能与容量**
- 每请求一次清理 DELETE + 无索引扫描（`auth_persistence.go:186`、`:94-97`）：`auth_refresh_session` 的 `expires_at` 谓词无可用索引，consumed/revoked 行从不删除。
- 客户门户最高频查询 `WHERE c.phone=$1` 缺单列索引（`customer_api.go:271-291`）：现有 `(owner_id, phone)` 前导列不匹配，每次全表扫 `crm_contact`。
- 媒体预签名无大小上限（`i6media/service.go:1175-1183`）：任意成员可 presign 500 GB 上传并真的灌进去；`i2_import_handlers.go:175` 用 `io.ReadAll` 把 100 MiB 整体读进内存。
- 出站事件吞吐约 0.5 条/秒（`worker/outbox.go:66-75`，`LIMIT 1` + 2 秒 tick），而每次业务写入都插一条，队列必然单调增长。
- AI 助手链路无任何限流与成本上限（`p2_assistant.go:136-260`），staff 角色即可持续消耗上游 LLM 额度。

**移动端**
- 弱网 401 刷新会误删 refresh token（`main.dart:46-59`）：refresh 请求超时也走 `sessionStore.clear()`，用户被迫重新短信登录，当前会话还会"假在线"。
- Android 未关备份（`AndroidManifest.xml:4` 无 `allowBackup`）：含手机号的明文会话快照进 Google 云备份与设备迁移。
- 本地通知在 Android 上静默失效：`flutter_local_notifications` 22.0.1 要求宿主声明 `ScheduledNotificationReceiver`，manifest 中没有，任务提醒到点无接收者。

**Web/小程序**
- 验证码冷却守卫检查了错误的字段名（`detail.js:23/105/114`：声明并检查 `codeCooldown`，实际写入 `codeCountdown`），且按钮只加了样式不加 `disabled` —— 客户端限流完全失效；`my-reservations.js` 更是毫无冷却逻辑。接真实短信供应商前必修。
- `dist/server.mjs` 是被提交的陈旧构建产物，落后 src 两处关键修改（仍会匿名 POST 已改为 409 的预订端点、缺 `joinV1Path`）。
- 公开表单无 CSRF/Origin 校验、无速率限制：`/consult` 直连 AI 顾问（烧 LLM 额度）、`/lead` 可向舍主 CRM 灌垃圾线索。
- Web 端缺全部安全响应头（CSP / nosniff / X-Frame-Options / Referrer-Policy / HSTS）；合同回执页 `/d/{token}` 可被任意站点 iframe 套壳。
- flash `result` id 经 Referer 泄漏，5 分钟内可重放读取他人咨询内容与 `session_token`。

**工程面**
- `Makefile:3-5` 无条件 `export AI_API_KEY` 到**所有**配方，本地跑 `make ci`/`flutter-*` 时真实付费 key 进入每个子进程环境。
- CI 缺顶层 `permissions:` 最小化；第三方 action（尤其个人维护的 `subosito/flutter-action@v2`）未 pin commit SHA。
- Caddy 站点无任何安全 header、无请求体大小限制。
- staging 不做生产配置校验（`config.go:127-131`）：`JWT_SECRET` 可留 `local-development-secret`、`SMS_MOCK_CODE` 可非空（固定验证码登录任意手机号），且暴露自助套餐激活 `POST /v1/entitlements/sandbox/activate`。

## 7. 测试有效性问题

**改动**（均在 `api/internal/store/principal.go`）

**遗留能力缺口（需产品决策）**

- 已经在用 ScolvPet 的宠舍主被邀请进别人的团队 → 邀请停在 `invited`，永远不生效。

## 11. 复核：P1-3.1 连接池死锁 → 升级 P0（已实测复现，未修复）

原报告把它列为 P1 且标注"疑似"。**实测确认，且比原描述更严重**：这不是性能退化，是**永久性进程级死锁**，必须重启才能恢复。

**实测方法**：`MaxConns=4` 的连接池，4 个并发 `POST /v1/auth/sessions/refresh`，20 秒未完成即判定死锁。结果连 `pool.Close()` 都卡住，测试进程被 Go 的 120 秒看门狗强杀。

**goroutine 栈证据**（同一互斥锁地址 `0x...4ac8`）：

```text
持锁者：
  auth.(*Service).Refresh          ← 持有 s.mu
   → store.(*Store).LookupRefreshSession
   → pgxpool.(*Pool).QueryRow
   → puddle.(*Pool).Acquire        ← 阻塞：等第二个连接

其余 3 个 goroutine（各持一个事务连接）：
  httpapi.(*Server).refreshSession
   → store.(*Store).RunIdempotent  ← 持有连接 #1（事务）
   → refreshSession.func1
   → auth.(*Service).Refresh
   → sync.(*Mutex).Lock            ← 阻塞：等 s.mu
```

循环等待成立：持锁者要连接，而连接被三个等锁者占着。

**为什么会自然发生**：生产 `DB_MAX_CONNS` 默认 8（`cmd/server/config.go:110`），**8 个用户同时刷新令牌**即触发——不需要攻击者，正常并发就会撞上。而且 `ParseAccessTokenContext` 同样抢 `s.mu`，一旦死锁，**所有带 Bearer 的请求全部阻塞**，整个 API 停摆。`http.Server.WriteTimeout` 不取消 request context，`pgxpool.Acquire` 也就不会超时退出。

**关于修复的重要判断**：只把 `persistence.*` 调用移出互斥锁**并不够**。去掉锁之后仍然是"N 个 goroutine 各持一个事务连接、又各要第二个连接"，在 `MaxConns=N` 时依然是纯资源死锁。真正的修复必须让 refresh 路径**不在事务内申请第二个连接**，二选一：

1. 给 `auth.Persistence` 增加接受 `pgx.Tx` 的变体，回调内复用同一连接；
2. 把 `s.Auth.Refresh` 移出 `RunIdempotent` 回调。

同时建议把互斥锁收窄到只保护内存 map（顺带消掉鉴权全局串行化），并给 `pgxpool.Acquire` 设超时兜底。

因为改法涉及 `auth.Persistence` 接口形状，属于需要决策的结构调整，本次**未动手修复**。复现探针已从仓库移除（留着会让 `make ci` 挂），修复时可据本节重建。

## 12. 复核：其余发现的真伪判定

### 需要升级

最具体的越权是：`listDocDocuments`（`p1_contracts.go:393`）把 `d.public_token` 选进结果并序列化（`p1_contracts.go:62` 的 `json:"public_token,omitempty"`），所以 **viewer 可以列出全部合同与回执的匿名访问令牌**，而这些 token 无有效期。此外可读财务流水、客户 PII、成员名册。

### 确认，但描述需修正

**XFF 伪造绕过 IP 限流**。确认，且比原描述多一个问题：`bucket_key varchar(200) PRIMARY KEY`（`0034:28`），XFF 首段超 193 字符触发 Postgres 22001，错误经 `ratelimit/postgres.go:66` 原样冒泡，`writeAPIError` 的 default 分支不匹配该错误 → **未认证可触发 500**。部署链确认可利用：Caddyfile 无 `trusted_proxies`、不清洗 XFF，Caddy 默认是追加而非覆盖，首段完全由客户端控制。

修正一处夸大：`sms:phone:` 桶（5 次/小时 + 生产 60 秒冷却）仍然有效，所以准确表述是"不能对单一号码无限轰炸，但可对无限多号码各发 5 条/小时"。行号也有偏移，实际在 `server.go:663-678`。

**令牌明文存进 idempotency_record**。确认，但原描述对暴露窗口的理解是反的。§9 对 `RunIdempotent` 的修复只收窄了**重放窗口**，没有收窄**落盘暴露**——`response_body` 只在同一个 key 再次被请求时才被清空，而登录场景的 key 常态是不复用的，所以那行明文令牌**永久留在库里**。真实暴露 = 永久存储 × 令牌有效期（access 1h / refresh 30 天）。

另一处修正：**远程重放不可行**，因为 `postgres.go:189` 要求 `request_hash` 匹配，攻击者需知道完整原始 payload（含一次性验证码或原 refresh token）。所以这是纯静态存储泄露风险（DB 备份、只读副本、SQL 注入），不是可远程触发的越权。补充：`p1_contracts.go:465` 的 issue 响应体含 `public_token`，同样明文落库。

对照之下，`auth_refresh_session` 里存的是 `digestHex()` 哈希——`idempotency_record` 是全库唯一的明文副本。

### 部分误报

**公开能力令牌进访问日志**。日志记录完整 path 属实（`server.go:595`），但"token 无有效期"**只对 documents 成立**：

### 移动端复核

**Android 任务提醒 100% 不会响（确认，是确定性功能 bug，非安全问题）**。三段证据闭合：`flutter_local_notifications 22.0.1` 的插件 manifest 全文只有两条 `uses-permission`、**零 receiver**（插件 README 从 v16 起明确要求宿主自行声明）；宿主 `AndroidManifest.xml` 里唯一的 receiver 是 `.TodayTasksWidgetProvider`；而插件用 `new Intent(context, ScheduledNotificationReceiver.class)`（`FlutterLocalNotificationsPlugin.java:572/595/621`）这种**显式 Intent 指向未声明组件**，AlarmManager 到点后广播无法投递、被系统静默丢弃。

**401 刷新回调抹掉凭据（确认，且比原描述严重）**。`main.dart:46-60` 的 `on Object` 捕获一切，把网络超时与真 401 同等处理。同一仓库 `app_state.dart:485-493` 就有专门区分两者的 `_isOfflineError()`，`restore()` 也用了它——只有这个 refresher 没用，属明确的内部不一致。

## 15. 连接池死锁修复记录（2026-07-26，方向一）

动手时发现比 §11 描述的还多吃一个连接：`RotateRefreshSession` 自己会再 `s.Pool.Begin()`。所以一次 refresh 实际占用**三个**连接——RunIdempotent 的事务、`LookupRefreshSession` 的 QueryRow、以及 Rotate 自己开的事务。

**改动**

| 文件 | 内容 |
|---|---|
| `api/internal/auth/service.go` | 新增可选接口 `RefreshTxPersistence` 与 `Service.RefreshTx(ctx, tx, token)`。持久化实现未提供该接口时回落到 `Refresh`，auth-only 单测不受影响。`RefreshTx` **不取互斥锁**——持久化路径不碰它保护的任何内存 map，取了只会把锁重新拖进等待环。 |
| `api/internal/store/auth_persistence.go` | 新增 `LookupRefreshSessionTx` / `RotateRefreshSessionTx`，SQL 抽到 `lookupRefreshSession` / `rotateRefreshSession` 两个私有函数与原方法共用，避免两份逐渐漂移。 |
| `api/internal/httpapi/server.go` | `refreshSession` 回调改调 `s.Auth.RefreshTx(ctx, tx, ...)`，整条轮换收敛到调用方那一个连接上。 |

**一处有意的行为差异**：`LookupRefreshSessionTx` 不做 `LookupRefreshSession` 里那次过期会话清理 DELETE。理由是在调用方事务里写共享行会放大它的锁足迹，而 `OwnerForRefresh` 已在同一请求的更早阶段（事务外）跑过同一次清理，所以清理并未丢失。

**验证**

- 新增 `api/internal/httpapi/auth_refresh_concurrency_test.go`：`MaxConns` 钉死为并发数（4），同时发起 4 个 refresh，要求全部返回 201。测试给每个请求设了 15 秒 context deadline——`pgxpool.Acquire` 遵守它，所以一旦回归是请求失败而不是整个测试进程卡死（写探针时就被卡死过一次）。
- 双向验证：把 handler 改回 `s.Auth.Refresh` 后，测试在 **15.03 秒**耗尽超时并以 `status=500` 失败；改回 `RefreshTx` 后 **0.02 秒**通过。
- `go build` / `go vet` / `gofmt` 干净；`go test -count=1 ./...` 注入四个测试库变量后 18 个包全 PASS。
- `scripts/public-reservation-smoke.sh` PASS（四个负例齐全）；`scripts/i1-smoke.sh` PASS（`owner isolation, idempotency, ETag, rules, events=4, published_outbox=2`）——后者正好覆盖登录/刷新/登出主链。

**仍未处理**

`ParseAccessTokenContext` 依然持 `s.mu` 做两次 DB 往返（其中一次是 `DELETE FROM revoked_token`），所以**每个带 Bearer 的请求仍然全局串行**。这不再导致死锁（不在事务内，不构成循环等待），但吞吐被压成单线程 DB 延迟的倒数，且每请求多一次写。属独立的性能问题，建议连同 §4 的"每请求清理 DELETE 移到后台任务"一起做。
